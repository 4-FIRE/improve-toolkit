# SessionStart、improve 与 memory 评估

评估日期：2026-09-10。源码基线：`bca76d0`，插件版本 `1.0.24`。
范围为提示词、技能规则和记忆工具对代理完成任务的影响。用户随后接受了调整方向。
下文保留变更前的评估依据，源码行号对应上述基线；文末记录实施情况。

## 判断与依据

插件的价值在于让后续会话获得模型原本不知道的用户偏好、项目事实和可复用方法。
启动摘要、按需召回、当前来源优先、跨宿主共享、写入冲突保护都支持这个定位。

目前主要负担是整理流程触发过广、工具检索能力有限，以及持久存储预算过小。
这些问题会影响任务选择、额外调用次数和历史信息的命中率。没有进行模型对照实验，
不能据此声称模型的推理能力下降，或给出速度、成功率变化的百分比。

已核对仓库和本会话安装版本的 `session_context.py`、`improve/SKILL.md`，两者一致。
实际注入的 `PERSONA_PROMPT` 为 1359 字符；improve 主文件为 3033 字符，技能候选文件
为 1005 字符。这些是字符数，不是 token 数，也不代表宿主完整上下文的大小。

[OpenAI 官方模型指导](https://developers.openai.com/api/docs/guides/latest-model#instruction-following)
说明模型可能对技能及其他指令文件中的含糊、冲突要求更加敏感，因此应检查这些文件
是否造成不必要的停顿。该说明支持检查方向，并不替代对本插件的行为实验。
[官方技能文档](https://learn.chatgpt.com/docs/build-skills)
说明技能采用按需加载：先提供名称和描述，选中后再读取完整技能。

## 三层职责

| 部分 | 已有价值 | 优先调整方向 |
| --- | --- | --- |
| SessionStart 注入 | 提醒记忆用途、召回时机与当前来源优先 | 聚焦插件约定；仅在有新信息时启动整理 |
| improve | 筛掉临时进度、重复信息和未经核验的结论 | 区分普通保存与复杂整理；无变更时允许直接结束 |
| memory / memory_recall | 持久保存、项目范围、稳定引用和冲突检测 | 提供确定的查找入口；明确返回量与存储量的不同预算 |

## 1. 每次任务结束加载 improve，把少量提示放大成固定流程

证据：[session_context.py](../../scripts/session_context.py) 第 35 行要求在任务结束时
加载 improve。主技能第 30—66 行列出七个步骤，包括为候选和相关旧条目分类、变更后
召回验证，以及没有变更时也报告 `no-op`、`reject`、`defer`。

例如，只回答一个代码位置或完成一次普通改名，本轮可能没有值得长期保留的信息，
但仍会触发加载和收尾要求。对更认真遵循规则的模型，这种要求可能增加额外工作。
这属于根据指令作出的行为推断，本次没有测量模型实际增加了多少耗时。

建议：任务结束时先做轻量判断；仅在出现持久的新信息、用户纠正、明确记忆要求、
相关旧记忆失效，或高价值流程候选时加载完整整理规则。无候选时直接结束。
只有实际写入、重要冲突或用户主动要求审计时，才报告记忆整理结果。

## 2. 通用人格和优先级表述应收窄到插件职责

证据：[session_context.py](../../scripts/session_context.py) 第 13—20 行包含
`EXTREMELY_IMPORTANT`、通用人格要求、反对弱技术想法的要求，以及用户当前请求
胜过任何内部准则的表述。

直接、诚实、尊重用户选择有价值；但通用人格同时受到宿主与用户指令控制。
插件再定义一次，会增加解释规则的负担，也可能使不同任务获得同一种强硬语气。
插件文本也不能改变宿主既定的指令优先级或权限。

建议：默认注入聚焦本插件的记忆用途与触发条件。人格偏好可以单独选择，或由用户
自己的操作指南维护。优先级精确限定为“用户当前要求优先于本插件默认整理流程”；
已经授权的范围内继续工作，不把技能授权扩展成普遍的确认要求。

## 3. improve 的价值门槛值得保留，完整整理流程需要按情况使用

证据：[improve/SKILL.md](../../skills/improve/SKILL.md) 的“持久、有用、新增、可验、
有界”五项门槛，能防止会话日志和随手推断污染长期记忆。安全边界也已明确区分
“读取信息”和“持久保存敏感信息”，并允许相关低风险偏好指导可逆决策。

普通新增偏好可以使用简短流程：核对是否重复、保存、检查工具返回。
矛盾处理、拆分迁移、批量清理和并发冲突则适合完整流程。前提是工具返回足够的
已保存信息来核对结果；当前写入返回值主要是引用、版本、用量和状态，尚未返回
完整规范化条目，因此减少回读应与工具改进配套。

第 55 行要求通过一次代表性查询核对“旧矛盾事实已消失”，而相关性查询没有返回
某条记忆并不能证明它已被删除。应通过稳定引用或更新结果确认具体条目变化；
代表性查询用于检查可发现性，不承担证明全库没有矛盾的任务。

技能候选文件已经允许“用户主动要求范围明确的变更”直接形成授权，这是应保留的
规则。可以在阅读顺序上先说明这条分支，避免把主动发现候选的筛选步骤误用于用户
已明确要求的技能工作。

## 4. 召回会漏掉含义相关的记忆，模型缺少确定的补救入口

证据：[memory_catalog.py](../../scripts/memory_catalog.py) 第 730—757 行将英文按词、
中文按连续双字拆分，用字词交集与整句子串计算匹配分数。
[工具 schema](../../servers/memory/tools.py) 第 376—432 行没有提供内部已有的
`browse`、`exact` 模式，也没有按 `entry_id` 获取详情或翻页的入口。

临时目录复现：保存“用户希望技术解释使用日常语言，减少行话。”后，查询
“用平实词写中文技能文档”返回 0 条；查询“技术解释”返回 1 条。

影响：模型可能误以为不存在旧偏好，或者反复猜关键词。提高模型推理能力不能保证
补上工具没有取回的信息。搜索不到也不能用来证明新事实没有重复条目。

建议：先提供简短索引、有限浏览和按稳定引用获取详情的入口，说明普通召回采用
关键词匹配。根据真实样例再决定是否需要更复杂的检索。当前规模没有充分理由直接
引入向量数据库。存储扩容时也要处理长条目超出单次预算后整条跳过的问题。

## 5. 长期存储与单次注入应采用不同的预算

证据：[memory_format.py](../../scripts/memory_format.py) 的默认项目正文总上限为
2200 字符，用户正文总上限为 1375 字符；[memory_catalog.py](../../scripts/memory_catalog.py)
另设启动摘要 800 字符、单次召回正文 2400 字符。这些值可以通过已记录的环境变量调整。

这不是实现错误，而是产品取舍。小总量适合少量精选便笺；若目标包括长期积累项目
经验，很容易迫使模型频繁压缩或淘汰仍有价值的旧事实。

建议：先完善查找入口，再放宽持久存储预算，同时保留严格的启动与单次返回预算。
扩容幅度根据真实项目的记忆数量和维护频率决定。本次没有确定新的默认值。

## 6. 完整工具返回量没有受到 max_chars 的同等限制

证据：[memory_catalog.py](../../scripts/memory_catalog.py) 第 311—316 行只累计
`content`，但 [tools.py](../../servers/memory/tools.py) 第 227—239 行还返回摘要、标签、
来源等字段。来源没有长度上限，标签只限制数量，没有限制单条长度。

边界复现：35 字符正文、4000 字符来源和一个 1000 字符标签，在
`recall_memory(max_chars=128)` 下返回 5398 字符，报告的 `returned_chars` 为 35。
这是构造的边界用例，不代表普通调用通常返回如此长的元数据。

建议：限制来源和标签长度，并让预算涵盖实际返回的信息；或者明确把现有参数称为
正文预算，为其他字段另设上限。保持 schema、实现和文档的含义一致。

## 7. 安全扫描应准确描述为有限粗筛

证据：[memory_catalog.py](../../scripts/memory_catalog.py) 第 35—61 行使用规则匹配。
正常事实 `The deployment account uses authorized_keys for authentication.` 会被
判为 `UNSAFE_CONTENT/ssh_backdoor`；同义的中文恶意指令可以未命中这些规则。

建议：保留“记忆是待核验事实，不授予执行权限”的边界；补充正常技术陈述的误报
测试，并收窄无条件词项。文档说明检查覆盖的范围，不把有限字符串规则描述为普遍的
提示注入防护。这些结果不代表宿主执行权限已被绕过。

## 经验的保存范围

当前主技能第 43 行已经允许把同一适用范围下的前提、失败表现和安全下一步写成
一条事实，因此“只保存事实”并不必然排除经验。建议进一步用例子讲清楚：

- 已验证的条件性经验：某版本在某条件下出现何种失败，依据在哪，可以进入记忆。
- 可重复执行的多步方法：适合进入技能候选，用户要求或接受具体方案后实施。
- 未验证的假设和单次结果：保留在任务记录或研究文档，不当作长期事实注入。

这一建议延续当前定位，不需要默认增加一个持久的假设库。是否扩大范围仍属待讨论项。

## 如何验证修改有益

保留现有程序测试，另外用固定任务比较：不启用插件、当前插件、简化后的插件。
宿主、模型、推理配置和项目初始状态保持一致；涉及学习效果的任务应包含下一会话。
在 Codex 和 Claude Code 分别运行后再判断跨宿主收益。

| 场景 | 观察结果 |
| --- | --- |
| 普通改名，没有持久新信息 | 任务正确性、额外工具调用、收尾报告、完成耗时 |
| 用户明确纠正稳定偏好 | 是否准确保存、下次换一种说法能否找到并正确应用 |
| 旧记忆与当前代码冲突 | 是否以当前来源为准，是否纠正相关旧条目 |
| 已授权修改技能 | 是否完成范围内工作，是否出现重复确认 |
| 含条件的失败经验 | 是否保留适用范围，是否误写成普遍规律 |
| 同义查询、长条目、存储接近上限 | 漏召回、额外查询、整理成本、有效信息损失 |
| 可疑记忆和正常 SSH 事实 | 是否保持权限边界，是否误拦有效内容 |

现有提示词契约测试主要检查指定文字存在与否，例如“1 week”和技能授权状态。
它们适合防止文本约定漂移，无法证明模型因此更快、更准确或更少打断用户。

## 接受后的实施

用户同意按上述方向修改后，已实施：

- SessionStart 聚焦插件约定，有新信息或相关需求时加载 improve；无变更时直接完成任务。
- improve 区分普通保存与复杂整理；技能文件先说明已有授权，再说明主动提案。
- 召回保留默认关键词查询，增加分页摘要索引、按 ID 读取及长正文分段读取；分页检查版本。
- 预算计入完整成功 JSON；写入返回可核对的条目；较长正文与旧元数据标记不完整。
- 存储默认值调整为项目 24000、用户 8000 字符，启动摘要仍为 800，召回默认仍为 2400。
  新存储值是可配置的起点，不代表已通过长期项目测量得出的最优值。
- 收窄 SSH 词项误拦，正文、摘要、来源与标签一致使用有限规则检查；保留记忆的信任边界。
- 用行为测试覆盖漏检后的查找路径、分页完整性、并发冲突、长正文、元数据预算和正常 SSH 事实。

这些变化没有引入语义检索或假设库。原有的同义查询可能仍然不命中，但现在可以通过
索引和稳定引用确定地找回。完整模型对照实验与跨宿主的真实任务收益仍未测量。

实施后验证：标准库测试 65 项、memory 集成测试 12 项通过，stdio MCP 端到端测试通过，
improve 技能格式校验和 `git diff --check` 通过。独立试用在临时项目中直接完成了用户
已授权的技能创建，并识别出两个清单的版本差异；没有修改真实记忆或发布任何内容。

完整插件校验仍报告三个已有技能的问题：eli5、grill-with-docs、roundtable 的
`disable-model-invocation` 和 `interface` 不符合当前校验器要求。对 `bca76d0` 原始
快照运行同一校验器得到完全相同的六项错误；本次未改变这些技能的调用方式。
校验使用仓库已有虚拟环境中的依赖，没有另行安装依赖。

改动保留在本地仓库，未提交、发布或更新已安装的插件副本。

## 2026-09-11：复核修复与漏检复盘

用户提出九组问题后，使用临时目录、实际工具适配层和当前源码逐项复现。旧 source
受污染时，显式清空或替换 source 原本就能保留 ID 完成修复；堵住的是 ID 本身受污染
的情况。512 是参数下限而不是任意条目的可读保证，原文已经约定预算不足错误；把下限
固定改成 1280 也不能覆盖需要 JSON 转义的合法元数据。这两项没有按最初指控直接修改。

用户授权后完成的修复：

- 环境变量中的正整数默认预算限制到合法范围，显式调用参数仍严格校验；无效环境值
  返回指出变量名的配置错误，同时覆盖首次创建 store 和已有 store 两条入口。
- relevant 保留 content，长条目返回正文前缀；只有 browse 返回摘要视图。搜索列表
  翻页和按 ID 续读正文各有明确的下一位置，客户端不必从一条短摘要重新猜测正文。
- 正文片段至少推进 256 字符，尾段允许不足 256；预算不足时提供 required_max_chars。
  继续严格计算完整 JSON，包括元数据、转义和 offset 位数，不自动突破调用者预算。
- 搜索、浏览和正文读取统一拒绝越界位置，允许恰好读到末尾。保留连续排序窗口，
  文档说明返回条数可能少于 limit，即使后面存在更短的条目。
- 安全错误指出字段但不回显可疑原文；通过 replace 的显式 repair_id 选项修复污染 ID，
  保留其他元数据、版本检查与最终条目检查。没有删除安全检查或自动清除旧来源。
- 提取条目摘要和写入回执正文上限常量；补齐术语、
  [ADR 0001](../adr/0001-layered-memory-and-addressable-recall.md)，恢复技能授权范围外内容
  保持不变的完成条件。仍有 max_chars 口径与下界的不兼容变化，发布时须明确版本策略。

### 为什么此前没有发现

这是实现和验收设计的不足，不是“测试全过”能够免责的情况，也没有证据能把漏检归因于
旧 SessionStart 提示词。程序测试、静态审查、真实代理行为实验是不同层面的证据。

1. **测试预期沿用了实现选择。** 原长条目测试直接断言 detail=summary，验证了我选的
   返回形式，却没有模拟旧客户端读取 content，也没有评价短首行摘要丢失的信息量。
   这是设计取舍评估不足，不只是漏写一个异常测试。
2. **把预算安全当成了可用性。** 主要检查“不超预算、能拼回正文”，没有要求每页的
   最小有效进度。固定样本能完整重建，不代表任意紧预算下不会退化为一字一页；后来
   复现还发现 offset 位数增长会使这种读取中途停住。
3. **兼容性只看显式参数，没有覆盖配置来源。** 下界从旧值提高后，调用参数受校验，
   环境变量却原样成为默认值。旧环境值、缺省参数、显式覆盖和冷启动入口应分别验证。
4. **安全验证只闭合了拒绝路径。** 验证污染被隔离和普通元数据能被覆盖，没有完整
   走过“隔离 → 识别字段 → 显式修复 → 保留其他元数据 → 回读”。因此漏掉污染 ID 的
   恢复出口，也没有检查修复与并发版本、ID 冲突的组合。
5. **没有按共享接口变化重新做文档验收。** 实施从提示词简化扩展到新的返回和分页约定，
   应同步检查术语、ADR、客户端迁移和版本边界；技能压缩时也应逐项保留原有授权约束。

此前“未发现明确缺陷”最多表示当时已检查的路径没有发现问题，不能推成这些边界均已
