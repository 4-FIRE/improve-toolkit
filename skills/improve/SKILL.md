# 复盘

把「下次还有用的东西」沉淀下来，把「再也用不上或被精化掉的旧条目」清理掉。**一沉一退要同时做**——只沉不退会撑爆预算，只退不沉会丢知识。

## 主动扫描，不等用户开口

复盘的价值上限取决于发现率，不是写入率。每次加载这个技能，按下面 5 个源逐一扫——任何一处冒头就捕捉：

1. **用户信号**
   - 纠正你 / 说"记住这个"/"别再这样" → 偏好进 `memory(target='user')`，事实进 `memory(target='memory')`
   - 确认了非默认做法（"对就是这样"/"perfect"/"可以"/"就这样"等显式肯定语）→ 记录方法 + 上下文。**纠正和确认同等重要**——只记纠正会让你过于保守。**仅"未反对"不算确认**，silence 可能只是没注意或暂时容忍
   - 召回类表达（"上次说过"/"之前不是…"）→ `session_search` 拉历史，提取跨会话仍有价值的事实补进记忆——**通常 0–1 条，极少超过 2 条**，别把整轮历史搬进记忆
2. **工具与子 agent 输出**——tool 结果暴露的非显而易见事实（路径、字段名、API 行为、错误码、配置约定、版本约束），子 agent 报告里的可复用结论。**这是最容易漏的源**——你常常把它们当一次性信息消费掉就过去了，要刻意停一下问"这条以后还会用吗"
3. **调试根因**——花力气查到的根因，回头记下"下次怎么避开"；只记结论，排障路径进技能
4. **存量对照**——本轮事实 vs 已有记忆/技能：矛盾 → 修，更精化 → 替换，重叠 → 合并
5. **技能使用反馈**——执行某技能时发现 outdated / 缺步骤 / 命令错 / 缺 pitfall / 触发不准（误触或漏触） → **当场** `skill_manage(action='patch')`，不等任务结束、不重写整个技能、只改有问题的部分

> 一处都没命中 → 直说"没什么要沉淀的"，不要为了复盘而强写。

## 沉淀决策树

**优先级：用户偏好/纠正 > 项目事实 > 过程性知识。** 一条防止再次纠正你的记忆，比十条"可能有用"的环境事实更值。

### 第一刀：事实 vs 过程

命中任一条就是技能，不是记忆：

- 含 shell 命令或代码片段（`mvn …`、`curl …`、`grep …`）
- 出现"修复方法"/"解决步骤"/"Fix:"/"How to apply:"
- A → B → C → D 形式的调用链路说明
- "如果 X → 执行 Y" 的条件分支
- 篇幅超过 3 行且含操作步骤

正确拆法：事实进记忆（如"项目存在 X 与 Y 的循环依赖"），排障/修复步骤进技能。

> 拿不准时回到最根的一问：**「这是『该做什么』（事实）还是『怎么做』（步骤）？」**——「该做什么」进记忆，「怎么做」进技能。

**新技能门槛**：`skill_manage(action='create')` 前先自问——"下个会话遇到同类问题，没这条会再次踩坑吗？" 答 yes 才建；否则只配做记忆，甚至不配。

### 第二刀：跟人走 vs 跟项目走

| Target | 判断 | 示例 |
| --- | --- | --- |
| **`user`** | 跟人走——换一个项目仍成立 | `User prefers Chinese responses`<br>`User insists on verifying claims before stating them` |
| **`memory`** | 跟项目走——换一个人接手也得知道 | `API rate limit is 10 req/min`<br>`Business identity field is bizCode not bizId`<br>`Project uses Node 18+` |

### 记忆写入前自检

写入前对每条都过一遍——格式没过这关，记忆就不要落盘。

**总则**：每条 = **原则 + Why**——记忆是触发器，不是百科全书。当事实有外部权威源（配置文件、文档、排班系统等）时再加一个**指向 source of truth 的指针**；无外部权威源的事实（用户偏好、项目本身的约定）直接陈述，不强行造指针。
**长度**：纯事实 1 行，带 Why 的偏好 1–2 行（约 30–200 字符）。超过 ~250 字符先自检：堆了多条事实（→ 拆条）还是塞了快照式枚举（→ 改指针式）？

- **陈述句，不写祈使句。** 记忆每轮都注入上下文。祈使句（"总是…"/"每次都要…"）会被后续模型当作当下指令执行，污染当时的请求；陈述句只是事实，不触发动作。
  - ✓ `User prefers concise responses without trailing summaries`
  - ✗ `Always respond concisely`
  - ✓ `Project uses pytest with xdist for parallel testing`
  - ✗ `Run tests with pytest -n 4`
- **偏好/纠正类附一句 Why。** 帮后续 session 判断边界情况，盲目遵守会变形；环境事实不需要 Why。
  - 偏好：`User prefers bundled PRs for refactors. Why: splitting was deemed unnecessary churn`
  - 事实：`Project uses Node 18+`
- **一条一个小颗粒度。** 不要堆叠多条到一条里，后续想改其中一条会很痛。
- **不要在内容里加 YAML frontmatter。** 存储格式由工具自己管理。
- **避免快照式枚举。** 凡是「此刻有 X、Y、Z」形式的清单——文件路径、流程步骤、对接人/角色、配置项、字段名……都要警惕。这是写入时刻的快照，新增项会漏、状态一变整段就 stale，**stale 比缺更危险**：后续会基于过期清单做推断和决策。改写成「**原则 + Why + 指向 source of truth 的指针**」，让真实环境（代码、文档、运行时状态、人）做权威；记忆只负责触发"去查"这个动作，不负责复刻当时的状态。
  - ✗ `Project uses libraries: requests, pydantic, sqlalchemy, redis, celery, ...`
  - ✓ `Project pins dependencies via pyproject.toml. Why: reproducible builds. Current set lives there, not in memory.`
  - ✗ `On-call: Alice (Mon), Bob (Tue), Carol (Wed)`
  - ✓ `Cross-team escalations go through on-call. Why: 避免私聊导致响应延迟. Current rotation in <团队公告 / 排班系统>.`
  - 例外：清单**永远不会变**（协议常量、物理限制、历史事实）才值得写死

## 不写什么

预算有限，先把噪音挡在门外——下面这几类不进记忆，避免挤掉真正有用的条目：

- **任务进度 / 完成日志**（"今天修了 X"、"PR #123 已合"）→ 用 `session_search` 召回，不进记忆
- **一次性事实**（本轮 commit hash、临时端口号、当前分支名、本次试错失败的命令）→ 下次 session 已无意义
- **可即时再查的常识**（语言/工具/标准协议的基础说明）→ 不写
- **已有记忆覆盖的事实** → 不重复写；新版本更精确就 `replace` 旧条，不让两条并存
- **当下指令翻版**（把"现在做 X"伪装成"系统应该做 X"的记忆）→ 这是任务，不是事实

## 腾退：删什么、改什么

> **记忆是写入时刻的快照，不是实时状态。** 基于记忆推荐文件/函数/配置前先验证还存在——记忆说"入口在 main.py"不等于 main.py 现在还在。腾退就是为了让快照少撒谎。

记忆是有限预算的工作集，不是 append-only 日志——超出字符上限会被截断丢内容。每写一条新记忆，问：「这次能腾出哪一条？」答不出来 → 这条新的也未必值得写。技能没有硬字符上限，但维护成本和触发污染是隐性预算——一个不再适用或重叠的技能会拉低相邻技能的触发准确率。

### 何时腾退记忆

| 情况 | 动作 |
| --- | --- |
| 被本轮事实证伪（如"入口在 main.py"但 main.py 已不存在） | `memory(action='remove')`——stale 比缺更危险 |
| 同一事实有更精确的新版本 | `memory(action='replace')` 旧条 |
| 多条记忆描述同一事实 | 合并成一条精确的，删散条 |
| 字符预算逼近上限（会话注入头部 `[N%]` ≥ 90%） | 按价值排序腾退：低价值环境事实 > 久未验证的事实 > 过程性记忆（这类本就该是技能）。**绝不动用户偏好/纠正类**——这类是最贵的记忆 |

### 何时腾退技能

| 情况 | 动作 |
| --- | --- |
| 底层工作流已废弃（命令/平台/API 不再适用） | 能 patch 就 patch；patch 不动就 delete——留着会误导下次使用者 |
| 两个技能触发条件重叠且产出相似 | 合并到更完善的那个；重写 description 划清边界 |
| 大段内容被另一技能更新版本覆盖 | 删被覆盖的，避免双份维护 |

> 真拿不准时留着，下次复盘再判断——"保留的负债"比"删错的损失"轻。

## 执行

1. **确认范围**——默认本轮会话；用户说"复盘今天"/"复盘上次 xxx"则用 `session_search` 拉对应历史一起扫。范围越大越要克制——只挑真正"下次还有用"的
2. **五源扫描**——用户信号 / 工具输出 / 调试根因 / 存量对照 / 技能反馈，逐项过一遍
3. **沉淀 + 腾退同时做**——`memory(action=add|replace|remove)` 与 `skill_manage(action=create|patch|edit|delete)`；记忆写入前对每条过一遍「记忆写入前自检」清单
4. **简报 3–5 行**——新增/patch/删除了哪些、为什么；不展开全文，给用户纠偏的机会

‼️ 不要把复盘做成仪式。没东西沉淀也没东西腾退就直说，有就动手。
