# 技能沉淀

本文件用于会话沉淀中的技能分支：判断本次交流中有依据、可复用的方法是否值得整理为新技能或补充已有技能，并在获得授权后实施。

## 值得沉淀的方法

技能补足模型容易判断错、遗漏或需要重复探索的部分，不重新教授一般操作。
从“这次弄明白了什么”出发，而不是复述“这次做了什么”。范围窄但依据扎实的方法，也值得保留。

区分成功所必需的条件与当时碰巧采取的动作。一次成功不证明整套过程都必要，也不证明其他场景同样适用。
例如，已确认代理缓冲导致流式内容延迟时，值得留下的是：

> 请求成功但持续收不到流式内容时，检查中间代理是否缓冲响应。普通请求成功不能排除这个问题。

不必保留当次查日志、重启、阅读文档的完整顺序。若原因尚未确认，就不能把尝试写成确定方法。
谨慎的是推广经验，不是要求方法覆盖所有场景。

## 编写原则

### 说明具体用途

技能名称和 description 会先于正文提供给模型。description 简短说明能力和具体适用场景，不要塞入操作步骤，也不要用宽泛主题词或反复强调“必须使用”来扩大触发范围。检查它与相关技能的分工，避免描述相互重叠或矛盾。

示例：描述数据库迁移技能。

- 范围过宽：创建并验证 Postgres 数据库结构迁移。处理数据库、查询、模型或持久化时使用。
- 范围明确：创建并验证 Postgres 数据库结构迁移。新增或修改迁移，或审查其上线方案时使用。

前者会让模型在处理普通数据库任务时也加载迁移技能，后者限定了实际用途。

### 按需提供资料

主文件保留共有指导，并说明如何选择适用流程。多种流程的详细说明、示例和脚本按需读取，链接旁说明使用条件。不要要求每次都读完所有分支，也不必把几条紧密相关的规则拆成多个文件。

### 规定结果和边界

写清目标、取舍依据、适用边界和完成标准，给模型选择做法的空间。
原则帮助判断未列出的情况；少量正反例帮助理解尺度，不用于穷举场景。
只有顺序、格式或具体操作会影响正确性时，才规定固定步骤。
不要把某次成功过程原样变成每次都要执行的流程，也不要把有用细节删成空泛口号。

### 按任务选择阅读范围

文档指引应说明“什么时候读”，而不是“每次先读”。保持引用和内容有效。
修改错字不需要先阅读整套资料或建立完整仓库地图。

示例：在 `SKILL.md` 中说明文档的阅读条件。

- 无条件要求：每次编辑前，阅读 `architecture.md`、`database.md` 和 `deployment.md`。
- 按任务选择：处理服务边界时读 `architecture.md`，修改数据库结构时读 `database.md`，准备部署时读 `deployment.md`。

### 写清授权和停止条件

区分用户需要决定的取舍与模型可以完成的执行细节。
不要让针对主动提案的确认步骤，阻断已经授权的修改和检查。
如果任务要求运行实现、检查结果并修复问题，完成标准应覆盖这些工作，而不是要求首次实现后就停下。
需要继续探索时，写清探索范围及结束条件；保留用户明确要求的审阅节点。

### 检查累积指令

将方法写入技能时，检查相关的项目指令和任务要求是否已有同一规则，避免重复或冲突。
对已有规则，区分真实约束与为旧模型补漏的提示。不能仅因某个模型能力提高，就删除权限或安全边界。
共享技能可能由不同模型执行；保留能改善结果的指导，不依赖某个型号必然具有良好判断。
只调整本次任务范围内的内容，不把技能修改扩展为全仓库指令清理。

## 提案与授权

发现有依据、值得复用的方法时再提案，不把技能建议作为每次任务的固定结尾。
普通操作和一次性修复留在当前任务中。已有相关技能时，优先考虑有针对性的修改。

检查相关技能和目标位置。简短说明解决哪类问题、关键方法、验证依据及拟写入的完整路径，让用户能判断是否接受。
无需在用户接受前写出完整技能及配套资源。

主动创建技能，或增加流程、改变判断规则、扩大适用范围等实质修改，须先获得用户确认。
不改变含义的错字和失效链接修正，不要求同样的提案流程。
用户已明确授权的创建或修改，直接完成范围内的工作和必要检查，不重复索取授权。

用户没有指定位置时，主动提案默认使用当前项目、当前宿主的技能目录：

- Codex、pi：`<project>/.agents/skills/<skill-name>/`
- Claude Code：`<project>/.claude/skills/<skill-name>/`

提案不阻塞原任务。用户未接受时，不实施所提议的创建或实质修改，也不反复提案；有新证据或用户重提时再考虑。
