# 把请求说清楚

把用户给出的疑问、需求、任务或当前讨论，改写成不了解本次对话的人也能直接讨论或执行的表述。只改写，用户没有同时要求回答或执行时，完成改写就停止。

## 改写要求

- **目标不变**：保留用户要弄懂的事、要做的决定或要得到的结果，不替用户决定没有表达过的偏好。原表述已经清楚时，保持原样。
- **先查后问**：从对话、文档、代码等资料中查清已经有什么、实际怎样运作、和期望有什么差距，用这些事实把含义不清的概念、范围和判断标准写具体。能写出对象、范围、关键约束和判断标准时就停止，不做全面调查。
- **检查预设**：检查原问题是否预设了未经证实的结论，或把选项限制得太窄；改写时也不加入自己的初步看法，猜测标为假设。例如，"接口太慢，是否该加缓存？"预设了原因和方案；改成"接口 P99 延迟 2 秒，找出主要耗时在哪里"。
- **形式随内容**：疑问写成一个问题，原问题含有多个问题时，选出答案最可能改变下一步行动的那个。需求或任务写成背景、要求和完成标准，分条列出。确有不同方向值得比较时，列出少量备选。每句话都应是目标、事实、判断标准、范围边界或完成标准。

## 输出

1. 改写后的表述。
2. 简短说明：补充了什么，关键事实的来源，哪些是你的理解。
3. 待确认的问题：只问会改变目标、范围或完成标准的，最多三个。证据已倾向某种解释时，说明倾向并请用户确认。其余缺口标为"待补充"，不编造条件。

用户回答后，整合答案，输出新版本。
